# AER Research Brief — 30 October 2026

Coverage: 23–30 October 2026; selected developments were published 24–26 October.

Scope: civilian aerial autonomy, controller evaluation, visual inspection and simulation reliability.

## Takeaway

This week's most important lesson is **evaluation design can change which controller appears best**. A large reproducible simulation study shows that tuning budget, preview information, fallback policy, actuator modeling and real command timing can reverse rankings or turn nominally successful runs into deadline failures. AER should therefore build a measured benchmark harness before choosing a controller or learned policy.

The [previous brief](2026-10-23.md), the current [phone recorder proposal](../drone-atlas/phone-mvp.md), and the live repository tree were reviewed. The repository contains no AGENTS.md. No working AER recorder, SITL integration or aircraft is assumed. Previous selections are not repeated.

## 1. Fair quadrotor-controller comparisons require more than RMSE

[Paper and submission history](https://arxiv.org/abs/2610.35165) — posted **26 October 2026**, v1.  
Status: arXiv preprint; peer review and independent replication were not verified.

**Demonstrated/author report:** the study compares cascade PID, hover LQR, boundary-layer sliding-mode control, linear MPC with fallback, preview-enabled MPC and a geometric SO(3) controller on the same nonlinear plant. Its primary study uses 556 episodes; a 1,462-episode confirmation study repeats the analysis with fresh realizations and larger tuning budgets. With matched tuning, BL-SMC moved from last to first in mean RMSE. Replaying measured command delays terminated three of four nominal MPC configurations on a desktop and all four on a Raspberry Pi 5; capping the solver at 100 iterations removed the tested deadline misses.

**Why it matters for AER:** selecting a controller from one headline error value is unreliable. AER's benchmark should record completion, failure, tuning effort, command timing, fallback activity and applied-input variation alongside tracking error.

**Limits/resources:** all evidence is simulation-based. The abstract establishes neither flight-hardware validation nor compatibility with PX4/ArduPilot. Results depend on the chosen plant, tasks, tuning search and delay traces. The arXiv record provides paper/HTML/source but does not link an official runnable code repository or packaged dataset; “reproducible” is an author description until the artifacts are independently run.

## 2. VisGeo-PipeTrack — adaptive visual servoing for civilian inspection

[Paper and submission history](https://arxiv.org/abs/2610.35342) — posted **26 October 2026**, v1.  
Status: arXiv preprint submitted to IEEE Transactions on Intelligent Transportation Systems; acceptance and independent replication were not verified.

**Demonstrated/author report:** the system detects pipe labels with YOLOv5, estimates relative position from geometric constraints, and uses recursive least squares plus rolling-horizon optimization to retune PID parameters. The authors report AirSim tests and physical experiments on a Tello UAV. In simulation, the proposed controller reports 3.26 s settling time and 3.52% mean tracking error; on the Tello it reports average-error reductions of 55.52%, 26.72% and 26.52% across three dimensions relative to standard PID.

**Why it matters for AER:** this is a compact prototype pattern: visual detection, explainable geometry, online system identification and a conventional controller. It is more approachable than an end-to-end navigation policy and maps to civilian inspection.

**Limits/resources:** label detection simplifies the perception problem, and pipe vibration is a narrow operating condition. Percentage reductions do not reveal absolute safety margins, full failure distributions or robustness to blur, occlusion and lighting. Tello results do not establish transfer to larger vehicles. No official code, trained weights, dataset, camera settings or complete hardware bill was verified from the primary record.

## 3. PX4/ROS 2 navigation v0.6.0 — explicit degraded-perception scenarios

[Release v0.6.0](https://github.com/formiat/px4-ros2-drone-nav/releases/tag/v0.6.0) — published **24 October 2026**.  
Status: open-source technical release under the repository's MIT license; simulation-oriented project, not a peer-reviewed study or flight-certified stack.

**Demonstrated/project report:** the release models smoke as a sensor-level phenomenon rather than a visual overlay. Its 3D-lidar profile uses weak echoes and neighboring returns as aerosol evidence; reported scenarios include going around a plume, crossing a smoky hall and returning when a corridor is judged unreachable. The release reports five successful runs for each cited scenario. The stereo attempt is explicitly described as incomplete: its optional detector can mistake a close illuminated wall for smoke and has thresholds tied to the test location. The broader repository provides PX4 SITL, ROS 2, Gazebo, one-command bootstrap and versioned scenario documentation.

**Why it matters for AER:** the engineering value is the evidence structure—fixed scenarios, whole-run manifests, explicit known failures and separation between what the simulator sets and what the onboard stack observes. This is a useful model for the sensor-corruption harness recommended last week.

**Limits/resources:** all release claims are self-reported by the project and simulation-only; no onboard computer or real aircraft has run the stack. First setup downloads several gigabytes, builds PX4 and needs Docker; GPU workflows require an NVIDIA container runtime. The smoke detector is not a general physical smoke model, and the stereo pathway is acknowledged as incomplete. Reusing the full stack would be high effort; borrowing its scenario/evidence conventions is lower risk.

These are AER engineering inferences inspired by the sources, not reproductions of their systems. Effort labels indicate relative complexity, not time promises. Hardware flight should follow offline replay, SITL, bench testing and an independent safety review.

## One priority

**Implement the controller-comparison contract as the first reusable experiment harness.** Start with deterministic Python simulation and a single PID baseline. Store scenario seed, trajectory, plant parameters, tuning budget, timing trace, completion/failure reason and summary metrics. Then add sensor corruption from last week's recommendation. Only after the harness is stable should AER add a second controller or connect PX4/ArduPilot SITL.

This creates a measurable bridge from compact learning exercises to R&D: algorithms can change while the evidence contract remains fixed.

- Definition of a safe fallback contract before any controller is allowed to continue after stale data or missed deadlines.
